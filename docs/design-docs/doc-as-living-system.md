# Documentation as a living system

Documentation in this harness is not prose written once and forgotten. It's a **system of record**: what
the agent can't see in the repo doesn't exist (core-belief 2). So docs are treated like code — kept by a
sensor, not by goodwill. Three disciplines make this work.

## 1. Per-folder index (progressive disclosure)

Each folder under `docs/` has an `index.md`: a short map of what lives there and when to read each file.
The agent enters the folder, reads the index, and goes deep ONLY into what the task needs. Without an
index it reads everything (fills context) or nothing (misses the rule). The index is the local table of
contents — the same role `AGENTS.md` plays for the whole repo.

## 2. Generated docs (`docs/generated/`)

Docs derived from code — DB schema, route/endpoint list, public types, environment variables — are **not
written by hand. They're generated by a script.**

- They live in `docs/generated/` and each file's top says "GENERATED — don't edit by hand; run `<cmd>`".
- Regenerated on build/CI (or by a hook), so they **never go stale**: if the schema changes, the doc
  changes in the same commit.
- Why: hand-written docs about something the code already defines are a second source of truth that will
  diverge. Generating eliminates the divergence by construction.
- Examples: `db-schema.md` (from Prisma/SQL), `api-routes.md` (from routes), `env.md` (from env vars).

How to build: a script that reads the source (schema, routes) and writes the `.md`; an npm command
(`docs:gen`); and ideally a CI check that fails if the generated output is out of sync (run the
generator, `git diff` must be empty).

## 3. Doc-gardening (the documentation sensor)

Docs rot — the code changes and the prose doesn't follow. The defense is the same one used for code: a
**recurring sensor**.

- **Computational:** a linter/CI job validating the knowledge base's structure — every `index.md`
  exists, internal links resolve, the generated output is in sync, each doc has an owner/date.
- **Inferential:** a recurring "doc-gardening" agent that scans docs for what **doesn't reflect the real
  code** (a cited function that no longer exists, a described flow that changed) and opens a small
  auto-mergeable fix PR.

Same pattern as code garbage collection (`QUALITY_SCORE.md`), applied to docs. Human taste captured once,
enforced continuously.

## The rule

Every doc is either **generated** (comes from code, can't lie) or **gardened** (a sensor keeps it
faithful). A doc that is neither is debt — it becomes a "graveyard of obsolete rules" the agent can't
tell is still valid. If you can neither generate nor garden a document, ask whether it should exist.
